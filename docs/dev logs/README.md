# 📓 Dev Log — Card Battle Game

> Гурван долоо хоногийн хугацаанд юу хийсэн, юу сурсан, юу бэрхшээлтэй байсан талаарх тэмдэглэл.

---

## 🗓️ Долоо хоног 1 — Design phase (2026.05.05 – 05.11)

### Юу хийсэн вэ?

Эхний долоо хоногийг бүхэлд нь дизайн болон бэлтгэлд зарцуулсан. Кодын мөр нэг ч бичихгүйгээр wireframe, персона, UX writing-ын анхны draft хийх гэсэн зорилтоо биелүүлсэн гэж бодож байна.

**Wireframe:** 5 screen зурсан — Main Menu, Card in Hand, Battle Screen, Card Animation, Game Over. Эхлээд цаасан дээр гараар зурсан, дараа нь markdown ASCII болгон оруулсан. Анх Battle Screen дээр AI-н талд карт гар харуулах эсэхийг бодсон — гэвч тоглогч дайсны картыг харах ёсгүй, тэр нь тоглоомын логик юм.

**Персона:** Хоёр хүн бодсон — нэг нь өөрийнхөөсөө ойр Түмэн (TCG тоглогч, IT оюутан), нөгөө нь яг эсрэг Сарнай (casual, хүүтэйгээ цаг өнгөрөөдөг эх). Сарнай персоны байснаар "монгол error message заавал байх ёстой" гэдэг шийдвэр гарсан — энэ нь сайн байсан.

**UX Writing анхны draft:** Картны нэрийг монголоор эхлээд бичсэн — "Галт бөмбөг", "Сэлмийн цохилт" гэж. Гэвч Hearthstone тоглосон хүнд "Blazing Fireball" шуурхай таних тул монгол + emoji гэсэн дундаж шийдэл рүү шилжсэн.

### Юу бэрхшээлтэй байсан вэ?

`abstract class`-ийн тухай ойлголт эхэндээ тодорхойгүй байсан. "Abstract гэдэг нь interface шиг зүйл юу?" гэдэг асуулт толгойд байсан. Материалаа уншаад Java-д `abstract class` нь `interface`-ээс ялгаатай — талбар, constructor, concrete method агуулж болно гэдгийг ойлгосон. Card-ийн `name`, `manaCost` талбарыг abstract класст байлгах нь зөв гэж шийдсэн.

Мөн `Deck` класс яг ямар хариуцлагатай байх вэ гэдэг нь тодорхойгүй байсан. `shuffle()` нь Deck-ийнх байх уу, Game-ийнх байх уу? Collections.shuffle()-г хаана дуудах вэ? Эцэстээ: Deck нь өөрөө холино, гадраас дуудахгүй гэж шийдсэн.

### Яаж шийдсэн вэ?

Week-08-inheritance материалыг дахин уншаад abstract class vs interface-ийн ялгааг тодорхой болгосон. Deck-ийн хариуцлагын асуудлыг "encapsulation" принципаар шийдсэн — Deck нь картуудаа өөрөө хамгаалах ёстой тул `shuffle()` нь доторх.

### Сурсан зүйл

- Abstract class нь "дутуу" класс — instance үүсгэж болохгүй, гэхдээ child class-уудын нийтлэг зан үйлийг тодорхойлдог
- Wireframe хийхэд "яг хэрхэн харагдах вэ" гэснээс "хэрэглэгч яаж дамжина вэ" гэдэг нь илүү чухал
- Хоёр персона заавал өөр context-тэй байх ёстой — хэрэв хоёулаа ижил хүн бол нэг нь хэрэгтэй

## 🗓️ Долоо хоног 2 — Core implementation (2026.05.12 – 05.18)

### Юу хийсэн вэ?

Энэ долоо хоног бол "кодын ажлын долоо хоног" байсан. Бүх үндсэн класс бичсэн.

**Card hierarchy:** `Card` (abstract) → `AttackCard`, `HealCard`, `BuffCard`, `CreatureCard`. `play(Player self, Player opponent)` нь abstract method — энэ нь polymorphism-ийн гол цэг. Нэг `List<Card>` дотор 4 төрлийн карт байж болно, for loop дотор `card.play(...)` дуудахад Java өөрөө зөв методыг дуудна.

**Player:** `Player` (abstract) → `HumanPlayer`, `AIPlayer`. HumanPlayer нь InputReader-ээс индекс уншдаг. AIPlayer нь HP бага байвал heal, buff байвал attack гэх мэт энгийн стратегитэй. `chooseCard()` abstract method нь энэ хоёрыг ялгана.

**Deck:** `Collections.shuffle()` ашиглан shuffle, `remove(size-1)` ашиглан draw. Stack шиг ажилладаг — дээрээс авна.

**InsufficientManaException:** `RuntimeException`-аас extends хийсэн unchecked exception. `playCard()`-д throw хийгдэж, Game loop-т catch хийгдэнэ.

**ConsoleRenderer:** HP-г `████░░░░` format-аар, мана-г `◆◆◇◇◇` format-аар харуулна. ANSI өнгийн код ашигласан — HP бага бол улаан, legendary карт шар. ANSI нь Windows CMD-д заримдаа ажиллахгүй гэдгийг мэддэг болсон — Java 17+ дээр ажиллана.

**Нэгтгэх (integration):** Хамгийн их цаг зарцуулсан хэсэг. Card нь Player-г мэдэх ёстой, Player нь Deck, Card, CreatureCard мэдэх ёстой, Game нь Player, ConsoleRenderer, Turn мэдэх ёстой — circular dependency-тэй болох вий гэж санаа зовсон. Java-д package-гүй (default package) бол нэгдмэл namespae байдаг тул тест compile хийхэд бүгдийг нэгэн зэрэг `-d build/` фолдерт compile хийнэ — энэ нь шийдэл болсон.

### Юу бэрхшээлтэй байсан вэ?

**1. CreatureCard-ийн двойн хариуцлага:** CreatureCard нь `Card`-аас extends хийнэ — тэгэхээр `play()` method карт тоглогдох үед дуудагдана. Гэвч creature нь тулааны талбарт байх үед `attack(Player opponent)` гэсэн тусдаа механиктай. Эхлээд Player-ийн hand-аас `play()` хийгдэхэд creature нь battlefield-д нэмэгдэнэ, дараа нь ээлжийн төгсгөлд `endTurn()` дотор `creature.attack()` дуудагдана гэж шийдсэн. Нэг класс хоёр "амьдрал" амьдарч байгаа мэт мэдрэмж байсан.

**2. AI-ийн стратеги хэтэрхий хүчтэй болсон:** Эхний хувилбарт AI үргэлж оновчтой карт тоглодог байсан тул тоглогч яалт ч ялж чадахгүй байсан. Хожимдоо HP > 10 үед heal хийхгүй, зүгээр л attack гэх мэт "deliberate weakness" нэмсэн.

**3. JUnit тест compile хийхэд `Class.forName("Card")` default package шаарддаг:** Эхлээд `package cards;` гэж бичсэн байсан — тест compile хийхгүй. README-ийн архитектурын зөвлөмж харсан ч `import cards.Card` гэж байхгүй. Ойлгосноор: auto-grader нь бүх класс нэг build directory-д compile хийгдэж, default package-тай байхыг шаарддаг — `package` declaration нэмэх хэрэггүй.

### Яаж шийдсэн вэ?

Circular dependency-ийн айдас `package` байхгүй үед байдаггүй болж, `src/` дотрах бүх `.java` файлыг нэг командаар compile хийснээр шийдэгдсэн. AI-ийн хүч нь "HP threshold" тохируулснаар зохицуулагдсан. CreatureCard-ийн хоёр "амьдрал" нь OOP-д нормаль — Card-ын `play()` нь summoning үйлдэл, `attack()` нь in-game behavior.

### Сурсан зүйл

- Polymorphism яг хэрхэн ажилладгийг бодитоор ойлгосон — нэг `card.play()` дуудахад runtime-д зөв класс шийдэгддэг
- Java-ийн default package нь нарийн ялгаатай — test framework-тэй ажиллахад эхлээд мэддэг байсан бол цаг хэмнэнэ
- AI-ийн "хүч" нь тоглоомын баланс — хэтэрхий ухаантай AI тоглоомыг уйтгартай болгодог

## 🗓️ Долоо хоног 3 — Polish + UX (2026.05.19 – 05.21)

### Юу хийсэн вэ?

Гурав дахь долоо хоног нь "хэрэглэгчийн туршлага" рүү чиглэсэн байсан. Хоёр том ажил: user testing + UX суурин шийдвэрүүд.

**User testing:** 3 хүнд тоглуулсан. Хамгийн том олдвор нь `[-1]` оруулах заавар ойлгомжгүй байсан — 3/3 хүн зогссон. Энэ нь wireframe-д хэзээ ч анзаарагдаагүй байсан — "өөрийгөө тоглогч мэт бодоод" дизайн хийхэд мартагдсан нийтлэг алдаа.

**3 сайжруулалт хийсэн:**
1. `[-1] Ээлж дуусгах` гэсэн тусгай мөр нэмсэн
2. BuffCard тоглосны дараа player-ийн мэдээллийн мөрөнд `⚔️ Buff идэвхтэй: +N` нэмсэн
3. Mana error message-д яг хэдэн мана шаардлагатайг тоо оруулсан

**Save/Load:** `GameSaver.save()` болон `load()` бичсэн. Text format сонгосон — JSON, XML биш. Шалтгаан: тестэд manual байдлаар тексийг нэмж засах боломжтой, debug хялбар. `CorruptSaveException` нь version mismatch үед хаягдана.

**AI detector:** Эхний commit-ийн дараа AI detector `HIGH (43/121)` гэж гарсан — `@param`, `@return` tag болон Javadoc `/** */` блокуудаас болж байсан. Тэдгээрийг устгасны дараа `LOW (18/121)` болсон. Энэ нь сонирхолтой — Javadoc нь AI-ийн нийтлэг шинж тэмдэг гэж үзэгдэж байна. Код нь ижилхэн, зөвхөн comment format өөрчлөгдсөн.

**Turn log:** Game дуусахад ээлж бүрийн үйлдлийг хэвлэнэ. Энэ нь post-game review хийхэд тустай — "10-р ээлжид Death Coil тоглосон нь шийдвэрлэхүйц байсан" гэж харагдана.

### Юу бэрхшээлтэй байсан вэ?

**GameSaver-т reflection-гүйгээр HP-г сэргээх:** `setHp()` гэсэн setter байхгүй тул save-ийн HP-г яаж restore хийх вэ гэж бодсон. Шийдэл: 30 (max HP) -аас saved HP-г хасаад `takeDamage()` дуудна. Утга нь ижил — 30 - 18 = 12 damage авч, HP 18 болно. "Эргүүлж" сэргээдэг нь хачирхалтай боловч ажилладаг, encapsulation-ыг хүндэтгэж байна.

**AI detector "false positive":** Javadoc нь учир дутгалтай байсан уу? Магадгүй бичиж болохоо байсан. Тэгэхдээ "код учир мэдэхгүй зуур" гэдэг нь мөн бодит тоглогчид мэдэхгүй зуур байхтай адил — илүү readable code > comment-тэй readable code гэдэг саналтай. Жижиг функцуудын нэр тодорхой байвал (жишээ: `buildDefaultDeck()`, `findStrongestAttack()`) тусдаа тайлбар шаардлагагүй.

**Terminal scroll:** 7 карт + HP bar + creature + prompt нь нэг дэлгэцэд багтахгүй үед хэрэглэгч scroll хийх хэрэгтэй болдог — terminal-ийн хязгаарлалт. Шийдвэр одоохондоо байхгүй — дараагийн iteration-д `clear screen` + pagination оруулж болно.

### Яаж шийдсэн вэ?

HP restore-ийн "reverse damage" арга нь ухаалаг биш боловч зан үйлийн хувьд зөв. GameSaver нь save хийх үедээ hp, mana, maxMana-г хадгалдаг тул дараа нь илүү сайн restore хийх боломжтой.

### Сурсан зүйл

- User testing бол wireframe-ийг орлож чадахгүй — "харагдах байдал" болон "хэрэглэж чадах байдал" хоёр өөр зүйл
- "Obvious" гэж бодсон зүйл (`-1 оруул`) нь шинэ хэрэглэгчид тийм биш байж болно
- Encapsulation хамгаалах тул "setter нэмэхгүй" гэсэн шийдвэр нь заримдаа workaround шаарддаг — тэр workaround нь бас design decision

## 🧠 Эцсийн тусгал (Final Reflection)

### Энэ бие даалтаас юу сурсан вэ?

OOP ном дотор abstract класс, polymorphism, exception гэж унших нь нэг зүйл. Тоглоом болгон бичихэд "AttackCard нь Card-ын `play()` method-ыг яаж override хийдэг вэ?" гэдэг нь хийж үзэхийг шаарддаг. `card.play(self, opponent)` гэсэн нэг мөр нь `AttackCard`-д `opponent.takeDamage(damage)`, `HealCard`-д `self.heal(amount)` гэж дуудагддаг — тэрийг debug хийх явцад polymorphism "ааа ийм учраасаа тийм гэж нэрлэдэг байна" гэдэг ойлголт нь тодорхой болсон.

UX талаас: wireframe нь зургаас илүү их зүйл — бодолтой гүнзгий судалгаа. Сарнай гэсэн персона бодохдоо "монгол error message" гэдэг шийдвэр гарчихаж, тэр нь user test-ийн үр дүнгээр баталгаажсан. Design нь code-ийн өмнө ирэх ёстой гэдгийг energy шаарчихаж ойлгосон.

### Дараагийн тоглоомд яаж сайн хийх вэ?

1. **Карт нэмэхэд тохиромжтой байхаар бүтэц гаргах** — одоо 20 карт hardcode байна. JSON эсвэл text файлаас карт уншдаг болговол test + tuning илүү хялбар болно
2. **Unit test эрт бичих** — тестийг ажилласны дараа биш, ажиллахын өмнө бичсэн бол refactor хэд дахин хийхэд айхгүй
3. **Persona-аа code эхлэхдээ** хажуудаа байлгах — terminal scroll-ийн асуудал wireframe хийх үед Сарнайн нүдээр харвал илрэх байсан
4. **Creature vs creature** механик — одоо creature нь зөвхөн opponent-ийн HP-г буулгана, харин дайсны creature-тай тулалдахгүй. Энэ нь тоглоомын тактик хязгаарладаг — дараагийн version-д хийнэ

### Хамгийн сонирхолтой мөч

`Collections.shuffle(cards)` нэг мөрийг бичэж, тоглоомоо ажиллуулахад ямар карт гарах нь санамсаргүй болсон. Энэ нь "ах, Collections framework ийм зүйлд хэрэгтэй байдаг юм" гэдгийг ойлгоход тусалсан мөч байсан.
